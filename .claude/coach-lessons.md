## Providers

- `[✓1 ✗0 · 2026-07-23]` **When** validating or listing a provider's models via the OpenAI SDK's `client.models.list()` against an OpenAI-compatible endpoint → **do** verify the provider's `/v1/models` actually returns OpenAI's `{"data": [...]}` envelope before relying on the SDK → **because** Together AI returns a **bare top-level array**, and `openai==2.30.0`'s `models.list()` raises on it — which silently turned every valid Together key into a 400 at the connect gate. Fix: list/validate such providers via `httpx` directly, accepting bare-array or enveloped (found by review-super on #2/PR #28).
- `[✓0 ✗0 · 2026-07-24]` **When** any code keys confirmation/UI state on a provider's `tool_use_id` → **do** thread the persisted assistant-row id (`msg_id`) end-to-end and match on it, and use index-based React keys for tool cards → **because** Gemini assigns positional ids (`call_{len(tool_calls)}`) that reset to `call_0` every `stream_turn`, so two distinct pending writes across turns share one id — a confirm keyed on `tool_use_id` alone can resolve/execute the WRONG write, and duplicate ids collide as React keys. The confirm SSE event already carried `msg_id`; the bug was dropping it client-side (#4/PR #37).
- `[✓1 ✗0 · 2026-07-25]` **When** any background surface (scheduler tick, daemon-thread worker, Telegram poller, cron) drives a provider call or the assistant `engine.chat` loop → **do** run the coroutine ON the app's main event loop — capture it once in `main.py`'s lifespan (`asyncio.get_running_loop()` → `assistant/background.set_main_loop`) and submit via `asyncio.run_coroutine_threadsafe(coro, main_loop).result(timeout)` (cancel the future on timeout so an abandoned call can't keep consuming the provider); offload only *blocking* work (`getUpdates`, DB calls) via `asyncio.to_thread` → **because** the provider async clients are module-cached AND event-loop-bound (`providers/anthropic_provider._client_cache` → `httpx.AsyncClient`): a throwaway `asyncio.run()` works ONCE then raises "Event loop is closed" forever, and a second long-lived loop sharing the cached client throws "attached to a different loop". Independently hit/confirmed by #6 (heartbeat), #7 (poller), and #16 (touch-count worker) on the 2026-07-25 team run — caught by a repo memory, NOT by any reviewer. Pure-algorithmic background jobs (dreaming) are immune, but confirm a background feature truly makes zero provider calls. The reusable shape is `assistant/background.run_background_turn` (PR #44); scheduler shutdown must be `wait=False` — a main-loop turn + `shutdown(wait=True)` on the lifespan's loop deadlocks.

## Testing

- `[✓1 ✗0 · 2026-07-23]` **When** a test suite mocks a provider **SDK object** (returning envelope-shaped fakes) → **do** add at least one test per provider that mocks the HTTP **transport** with the REAL wire shape (e.g. `httpx.MockTransport` returning Together's bare array) → **because** SDK-object mocks can't catch wire-format mismatches or catalog-content bugs (Google returning TTS/image models that name-based tier inference then picks as defaults) — both were caught on #2 only by running the real pinned SDK against a mocked transport.
- `[✓1 ✗0 · 2026-07-23]` **When** a service does two SELECTs in one transaction and treats them as one consistent snapshot → **do** issue `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` as the FIRST statement of that transaction → **because** Postgres' default READ COMMITTED takes a new snapshot per statement, so the pair can see different states; the transaction-scoped form resets at commit and is safe on a pooled connection, unlike `SET SESSION`, which leaks across checkouts (CredentialStore, #2).
- `[✓1 ✗0 · 2026-07-23]` **When** a monkeypatched factory wraps the very symbol it patches (e.g. `monkeypatch.setattr(httpx, "AsyncClient", lambda *a, **k: httpx.AsyncClient(...))`) → **do** capture the original into a local first (`real = httpx.AsyncClient`) and call that → **because** the lambda body resolves the patched name → infinite recursion (#2).
- `[✓7 ✗0 · 2026-07-27]` **When** tests or PR evidence need a real local Postgres → **do** use the shared `cake_os-postgres-1` container (port 5432, role `cake`/`cake_dev`; `psql` may be absent — create/seed via the venv's psycopg2) and create/drop throwaway databases in it (integration suite: `cakecrm_it_crm_<pid>`; PR-evidence app boots: `cakecrm_ev<N>` / `cakecrm_evidence_<N>` / `cakecrm_pr<N>`) — never compose a new Postgres server, never `docker compose up` CakeCRM's own compose (it maps 5432:5432 and collides), and never `docker compose down` the shared one → **because** the shared container is already running for cake_os dev, throwaway DBs keep runs isolated and cleanup trivial, and a second server fights over port 5432 (#2; #3/PR #31; #15/PR #34; #19/PR #42; all seven evidence boots on the 2026-07-25 team run; ✓+2 on the 2026-07-27 team run — #20 and #21 booted evidence concurrently on the same container with zero collision, purely because their DB names were unique).
- `[✓0 ✗0 · 2026-07-27]` **When** adding a SQL-aggregation service fn in `backend/crm/` that must pass the default (hermetic) `pytest` gate → **do** split it into thin `pg_fetch*` calls + PURE module-level Python shapers (all ratio/guard/bucket/coercion logic), unit-test the shapers with mocked rows, put the REAL SQL semantics behind `@pytest.mark.integration`, and state that coverage boundary in the PR body → **because** the default suite mocks the pg helpers so the SQL never executes: a `sql_containing("…")` substring assertion proves the string was BUILT, not that `FILTER`/`GREATEST`/`EXTRACT` behave — so an opaque one-blob query goes green in CI while being semantically broken, and the integration test that would actually run it is deselected by `-m "not integration"` (#20/PR #49).

## Tooling

- `[✓1 ✗0 · 2026-07-23]` **When** running `ruff` while a sibling PR owns the repo's lint config (`ruff.toml` not yet merged) → **do** run `ruff check --config <that file>` scoped to YOUR files, never `ruff check . --fix` tree-wide → **because** default ruff selects far more rules than the repo config (`F,E,W,I` here), and a tree-wide `--fix` re-sorts imports in files outside your change, creating spurious diffs that conflict with the sibling PR. Revert any out-of-scope files ruff touches (#2 vs #10/PR #27).
- `[✓0 ✗0 · 2026-07-25]` **When** committing via `git add <explicit list>` in an automated flow → **do** NOT suppress stderr (`2>/dev/null`), and verify with `git show --stat <sha>` (or a clean `git status`) that the commit captured what you intended → **because** one stale/nonexistent pathspec (e.g. an old path after a `git mv`) aborts the ENTIRE add; with stderr hidden the "commit" silently captured only what was already staged, while tests kept passing against the WORKING TREE — the drop was invisible until the Stage-4 reviewer found uncommitted fixes including a P1 (#16/PR #45).
- `[✓0 ✗0 · 2026-07-27]` **When** a docstring or comment asserts a resource is "bounded" / "safe" / "eventually cleans itself up" NEXT TO concurrency, socket, thread, or lock code → **do** treat the claim as a hypothesis to DISPROVE — construct the exact scenario in which it does not hold — before letting it stand → **because** on #17/PR #51 a docstring claimed a leaked scan worker was "bounded — the socket eventually errors", and that false assumption is precisely what let an **unbounded** thread+socket leak (one per scan interval under a persistent transport hang) ship looking safe through review-super AND the first Codex pass. Without a transport timeout a stalled socket may never error, so "eventually" was never guaranteed. A comment asserting a safety property must be EARNED by the mechanism directly below it, or it re-arms the trap for the next reader (repo instance of the global "documenting why something is safe is not the same as proving it").
- `[✓0 ✗0 · 2026-07-27]` **When** comparing two ISO-8601 UTC timestamps (`…Z` — a review's `submitted_at` vs your push time) in a shell poll → **do** compare them LEXICOGRAPHICALLY (`[[ "$a" > "$b" ]]`) — they sort chronologically — never `date -j -f "%Y-%m-%dT%H:%M:%SZ"` → **because** BSD `date -j -f` treats the trailing `Z` as a LITERAL and parses the time in LOCAL tz, so every comparison is silently off by the tz offset; it cost two bogus "re-reviewed" false-positives on #18/PR #52's settle poll.
- `[✓0 ✗0 · 2026-07-25]` **When** multiple review stages re-flag a gap you already deliberately deferred (e.g. races coupled to deferred multi-user work) → **do** treat the repeat as the SAME gap seen through a new lens, keep the deferral, and pre-empt the next stage: drop an inline `# … (tracked in #N)` comment at each flagged spot plus a PR-body deferral section → **because** un-deferring under repeated-reviewer pressure is the confirmation-bias trap, and the settle-loop's fresh Codex review WILL re-raise it unless the deferral reads as "verified → documented" in the code itself (#8/PR #47, connection-race cluster → #43; mirrors the global "unanimous P1 can still be right to defer" lesson).

## Backend

- `[✓0 ✗0 · 2026-07-24]` **When** a file-backed config loader (e.g. `backend/branding/storage.py`) derives a field from an external artifact's existence — like `has_logo` from `LOGO_FILE.exists()` → **do** compute that derived field in EVERY return branch (the no-config-file default, the happy path, AND the corrupt/except path), never only the happy path → **because** the artifact can be written before any config JSON exists (logo uploaded via `POST /logo` first), so a happy-path-only derivation reported `has_logo:false` after reload despite the file existing (#9/PR #33).
- `[✓0 ✗0 · 2026-07-24]` **When** allow-listing image types for the branding logo (stored as fixed `logo.png`, served by `GET /api/branding/logo` with filename-guessed content-type and NO auth) → **do** exclude `image/svg+xml` from both `ALLOWED_IMAGE_TYPES` (backend) and the frontend accept list → **because** every logo is served as `image/png`; browsers content-sniff raster formats but NEVER SVG, so an SVG silently never renders (the graceful `BrandLogo` fallback masks it), and serving real SVG from the unauthenticated endpoint is a stored-XSS surface (#9/PR #33).
- `[✓0 ✗0 · 2026-07-24]` **When** implementing a human-confirmation gate for non-idempotent write tools with a claim/execute/persist flow → **do** commit an `executing` marker BEFORE running the tool (two-phase), not hold a row lock across execution and not execute-then-claim → **because** the alternatives are worse: a lock held across execution risks rollback-after-side-effect → retry double-executes; execute-then-claim races two approvers into double execution. Mark-executing-first guarantees NO double-execution (retry sees not-pending → `already_resolved`) at the cost of a rare, inspectable stuck `executing` state on mid-flight crash — when a reviewer flags that stuck state as a P1, the right response is to document the deliberate tradeoff, not "fix" it into a double-write design; full exactly-once needs idempotency keys on the CRM ops (#4/PR #37).
- `[✓0 ✗0 · 2026-07-25]` **When** a service reads multiple rows from ONE psycopg2 cursor across several `execute()` calls and later calls `row_to_dict(cur, earlier_row)` → **do** convert each fetched row to a dict IMMEDIATELY after its `fetchone()`, before the next `execute()` → **because** `row_to_dict` derives column names from `cursor.description`, which every `execute()` rebinds to its own statement's columns — a late conversion zips the FIRST row against the SECOND query's columns into a silently wrong dict. In `provenance_service.confirm()` the live-value read was always `None` → confirm always `{"stale": true}` → the feature was fully broken (#16/PR #45, P1). **Testing corollary:** a hermetic test that monkeypatches `row_to_dict` to identity MASKS this class — for multi-statement `SELECT … FOR UPDATE` flows, use a fake cursor tracking per-`execute` `.description` and let the REAL `row_to_dict` run.
- `[✓0 ✗0 · 2026-07-25]` **When** parsing an LLM's structured reply where "never fabricate" is the contract (a count/score computed from untrusted note text) → **do** accept ONLY exact-key valid JSON (whole reply or one embedded `{...}`), drop bare `key: value` / first-integer regex fallbacks, clamp the value range, and reject truncation `stop_reason`s where the provider exposes them → **because** a lenient regex parses a model echoing an injected `"touch_count: 99"` from the fenced evidence — strict JSON bounds a successful injection to at most a wrong estimate, never a trusted-looking fabrication (#16/PR #45).
- `[✓0 ✗0 · 2026-07-25]` **When** giving an autonomous/background AI turn tool access (no human present to confirm writes) → **do** restrict it to a SERVER-ENFORCED allowlist of read tools + a single notify-style tool — enforced at BOTH advertisement (`provider_tools(allow=…)`) and execution (fail-closed) — and pass untrusted content (reminder/CRM text) in the USER message, never the system prompt → **because** auto-approved writes over injectable text are a real prompt-injection surface and a textual "treat this as data" instruction is not a boundary; reads+notify is both the airtight answer and a net simplification — worst case an injection sends one notification (#6/PR #44).
- `[✓0 ✗0 · 2026-07-25]` **When** mapping a service-layer error to an HTTP status in a router → **do** return a structured `code` from the service and switch on it → **because** substring-matching the message text means a future reword silently flips the status (404↔400↔409) with no test failure; three reviewers independently flagged the substring version (#6/PR #44).
- `[✓0 ✗0 · 2026-07-25]` **When** computing the next occurrence of a recurring item after downtime → **do** compute directly from `now` (seed cron at `max(due, now)`; jump daily/weekly series to now's date) with a small bounded scan → **because** iterating occurrence-by-occurrence from the stale `due_at` under a fixed cap silently returns None and TERMINATES the series with no error — a weekly series capped at 14 iterations died after two weeks; a per-minute cron capped at 4000 died after ~3 days (#6/PR #44).
- `[✓0 ✗0 · 2026-07-25]` **When** any secret rides an HTTP URL (Telegram's `/bot<TOKEN>/…`, presigned URLs, keys as query params) and the app uses httpx → **do** `logging.getLogger("httpx").setLevel(logging.WARNING)` → **because** httpx logs every completed request at INFO with the FULL URL, so root-INFO logging leaks the secret into app logs; redacting exceptions is not enough — the request log line is separate (#7/PR #39, caught only by the Codex PR reviewer).
- `[✓0 ✗0 · 2026-07-25]` **When** you create a single long-lived asyncio background task in the FastAPI lifespan (no supervisor) → **do** wrap the loop body in a broad `except Exception:` that logs and backs off, keeping `except asyncio.CancelledError: raise` ahead of it → **because** one transient error (a DB blip in a pooled `pg_*` call) escapes the loop and permanently completes the sole task — nothing restarts it, so the feature silently dies until process restart; four independent reviewers flagged the same gap (#7/PR #39).
- `[✓0 ✗0 · 2026-07-25]` **When** a button/callback confirmation flow (Telegram or web) resolves against a server-side "current pending" pointer → **do** bind each button to its originating batch (e.g. an 8-char `msg_id` prefix in `callback_data`, well under Telegram's 64-byte cap) and reject on mismatch → **because** positional-id providers (Gemini's `call_0` resets every turn) let a STALE button resolve a *different* current write — approving the wrong action; sibling of the Providers `msg_id` instinct (#7/PR #39).
- `[✓0 ✗0 · 2026-07-25]` **When** a new feature must fence untrusted content passed to the model (email bodies, tool results) → **do** grep for the existing wrap primitive (`delimiters.wrap_untrusted_file` + its paired system-prompt instruction) and extend it → **because** a hand-rolled `<tag>…</tag>` with a static closing tag is forgeable and un-instructed; the nonce fence (random id in open+close) is the codebase's established forge-proof pattern (#8/PR #47).
- `[✓0 ✗0 · 2026-07-25]` **Postgres/SQL gotchas (memory + dreaming port, #5/PR #46):** (a) `GREATEST`/`LEAST` IGNORE NULL inputs — `GREATEST(0, NULL)` = `0`; when NULL must propagate (never-retrieved fact → "recency 0"), CASE-guard it or the clamp reads as "touched just now". (b) `EXTRACT(EPOCH …)/86400.0` is `numeric` → psycopg2 returns `Decimal`, and `float * Decimal` raises TypeError — cast `::double precision` in SQL; hermetic tests can't catch it. (c) `to_tsvector`'s default parser emits COMPOUND lexemes for emails/URLs/dates (`'dana@acme.com'` is ONE lexeme a plain-word query never matches) — index a `translate(text,'@./:-','     ')` split copy in the generated column. (d) the `simple` FTS config keeps ALL function words, so OR-ing every query token matches facts on filler ("at"/"to" in predicates) and phantom-inflates retrieval tracking, defeating usage-based archival — filter function words on the QUERY side (with an all-filler fallback; exclude name/acronym homographs like will/may/us).
- `[✓0 ✗0 · 2026-07-25]` **Asyncio/datetime gotchas (scheduler work, #5/PR #46):** (a) subtracting two aware datetimes sharing the SAME `tzinfo` object does NAIVE wall-clock math (documented) — across DST it's off by the shift; use `.timestamp()` deltas (different-tzinfo comparisons convert correctly — only same-tzinfo math is the trap; Codex-caught).
