## Providers

- `[✓1 ✗0 · 2026-07-23]` **When** validating or listing a provider's models via the OpenAI SDK's `client.models.list()` against an OpenAI-compatible endpoint → **do** verify the provider's `/v1/models` actually returns OpenAI's `{"data": [...]}` envelope before relying on the SDK → **because** Together AI returns a **bare top-level array**, and `openai==2.30.0`'s `models.list()` raises on it — which silently turned every valid Together key into a 400 at the connect gate. Fix: list/validate such providers via `httpx` directly, accepting bare-array or enveloped (found by review-super on #2/PR #28).
- `[✓0 ✗0 · 2026-07-24]` **When** any code keys confirmation/UI state on a provider's `tool_use_id` → **do** thread the persisted assistant-row id (`msg_id`) end-to-end and match on it, and use index-based React keys for tool cards → **because** Gemini assigns positional ids (`call_{len(tool_calls)}`) that reset to `call_0` every `stream_turn`, so two distinct pending writes across turns share one id — a confirm keyed on `tool_use_id` alone can resolve/execute the WRONG write, and duplicate ids collide as React keys. The confirm SSE event already carried `msg_id`; the bug was dropping it client-side (#4/PR #37).

## Testing

- `[✓1 ✗0 · 2026-07-23]` **When** a test suite mocks a provider **SDK object** (returning envelope-shaped fakes) → **do** add at least one test per provider that mocks the HTTP **transport** with the REAL wire shape (e.g. `httpx.MockTransport` returning Together's bare array) → **because** SDK-object mocks can't catch wire-format mismatches or catalog-content bugs (Google returning TTS/image models that name-based tier inference then picks as defaults) — both were caught on #2 only by running the real pinned SDK against a mocked transport.
- `[✓1 ✗0 · 2026-07-23]` **When** a service does two SELECTs in one transaction and treats them as one consistent snapshot → **do** issue `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` as the FIRST statement of that transaction → **because** Postgres' default READ COMMITTED takes a new snapshot per statement, so the pair can see different states; the transaction-scoped form resets at commit and is safe on a pooled connection, unlike `SET SESSION`, which leaks across checkouts (CredentialStore, #2).
- `[✓1 ✗0 · 2026-07-23]` **When** a monkeypatched factory wraps the very symbol it patches (e.g. `monkeypatch.setattr(httpx, "AsyncClient", lambda *a, **k: httpx.AsyncClient(...))`) → **do** capture the original into a local first (`real = httpx.AsyncClient`) and call that → **because** the lambda body resolves the patched name → infinite recursion (#2).
- `[✓3 ✗0 · 2026-07-24]` **When** tests or PR evidence need a real local Postgres → **do** use the shared `cake_os-postgres-1` container (port 5432) and create/drop throwaway databases in it (integration suite: `cakecrm_it_crm_<pid>`; PR-evidence app boot: `cakecrm_app`) — never compose a new Postgres server → **because** the shared container is already running for cake_os dev, throwaway DBs keep runs isolated and cleanup trivial, and a second server fights over port 5432 (#2; #3/PR #31; #15/PR #34).
- `[✓0 ✗0 · 2026-07-24]` **When** building/reviewing a feature that goes through the multi-provider AI ABC (`stream_turn`/`add_tool_results`/`build_tool_turn`) and testing it only with a scripted FakeProvider → **do** also verify each provider's real message-shape *contract* — assert no orphaned `role:'tool'` messages survive assembly, assert the wrap-up call passes tools when the history carries tool blocks — via shape-contract tests or a live per-provider smoke → **because** a hermetic fake stream validates loop control flow but NOT what the real wire rejects: review-super's final stage found TWO P1s the 296-test hermetic suite structurally could not — Anthropic 400s on a wrap-up `stream_turn(messages, [], …)` when the history carries tool_use/tool_result (empty tools → `NOT_GIVEN`), and `_coalesce_consecutive` merging a narration row into an OpenAI-shaped `{role:assistant, tool_calls:[…]}` row dropped `tool_calls`, orphaning `role:'tool'` messages → OpenAI/Ollama/Together 400 the conversation forever. Both invisible to Anthropic-shaped fakes (#4/PR #37).
- `[✓0 ✗0 · 2026-07-24]` **When** adding a **polymorphic** CRM table (`entity_type`/`entity_id`, no FK — e.g. `crm_chatter`) that attaches to deals/contacts → **do** add it to EVERY lifecycle site, not just one: `_CRM_TABLES`, `_truncate_all`, `is_crm_empty`, `_crm_empty_in_txn`, the `seed_demo_data` empty-guard + setval loop, and each `delete_*` cascade — and pin the exact `TRUNCATE` string in a service test → **because** with no FK, Postgres reuses a `SERIAL` id after `TRUNCATE … RESTART IDENTITY`, so any missed cleanup site lets a new deal/contact **inherit a deleted entity's notes** (ID-reuse orphan). Verified by integration test on #15/PR #34 (count→0 and a reused id sees `[]`).

## Tooling

- `[✓1 ✗0 · 2026-07-23]` **When** running `ruff` while a sibling PR owns the repo's lint config (`ruff.toml` not yet merged) → **do** run `ruff check --config <that file>` scoped to YOUR files, never `ruff check . --fix` tree-wide → **because** default ruff selects far more rules than the repo config (`F,E,W,I` here), and a tree-wide `--fix` re-sorts imports in files outside your change, creating spurious diffs that conflict with the sibling PR. Revert any out-of-scope files ruff touches (#2 vs #10/PR #27).

## Backend

- `[✓0 ✗0 · 2026-07-24]` **When** a file-backed config loader (e.g. `backend/branding/storage.py`) derives a field from an external artifact's existence — like `has_logo` from `LOGO_FILE.exists()` → **do** compute that derived field in EVERY return branch (the no-config-file default, the happy path, AND the corrupt/except path), never only the happy path → **because** the artifact can be written before any config JSON exists (logo uploaded via `POST /logo` first), so a happy-path-only derivation reported `has_logo:false` after reload despite the file existing (#9/PR #33).
- `[✓0 ✗0 · 2026-07-24]` **When** allow-listing image types for the branding logo (stored as fixed `logo.png`, served by `GET /api/branding/logo` with filename-guessed content-type and NO auth) → **do** exclude `image/svg+xml` from both `ALLOWED_IMAGE_TYPES` (backend) and the frontend accept list → **because** every logo is served as `image/png`; browsers content-sniff raster formats but NEVER SVG, so an SVG silently never renders (the graceful `BrandLogo` fallback masks it), and serving real SVG from the unauthenticated endpoint is a stored-XSS surface (#9/PR #33).
- `[✓0 ✗0 · 2026-07-24]` **When** implementing a human-confirmation gate for non-idempotent write tools with a claim/execute/persist flow → **do** commit an `executing` marker BEFORE running the tool (two-phase), not hold a row lock across execution and not execute-then-claim → **because** the alternatives are worse: a lock held across execution risks rollback-after-side-effect → retry double-executes; execute-then-claim races two approvers into double execution. Mark-executing-first guarantees NO double-execution (retry sees not-pending → `already_resolved`) at the cost of a rare, inspectable stuck `executing` state on mid-flight crash — when a reviewer flags that stuck state as a P1, the right response is to document the deliberate tradeoff, not "fix" it into a double-write design; full exactly-once needs idempotency keys on the CRM ops (#4/PR #37).

## Frontend

- `[✓0 ✗0 · 2026-07-24]` **When** a UI affordance keys off an async `/api/setup/status` fetch (`ai_ready` / `credentials_present`) and the fetch fails → **do** preserve the "unknown" state (leave it `null`), don't collapse it to a concrete `false` — and gate the "add an AI key" nudge on `!credentials_present`, not `!ai_ready` → **because** collapsing to `ai_ready:false` turned a supposedly-inert `AssistantLauncher` into one actively routing users who may have a valid key to `/setup`; `null` keeps the launcher inert and the nudge suppressed, and a key can exist while the active model is unresolved (#9/PR #33).

## Porting

- `[✓1 ✗0 · 2026-07-24]` **When** porting a chatty (SQLite) frontend date helper that does `new Date(iso + 'Z')` → **do** drop the `'Z'` — or append it only when the string carries no zone (`/[Zz]|[+-]\d\d:?\d\d$/.test(iso)`) → **because** chatty's SQLite `created_at` is a naive TEXT string (`datetime('now')`, no offset) so appending `Z` was correct there, but CakeCRM stores `TIMESTAMPTZ` and psycopg2 returns tz-aware datetimes that `core/postgres._postprocess_value` `.isoformat()`s to `...+00:00` — appending `Z` yields `...+00:00Z`, which `new Date()` parses as **Invalid Date** without throwing, so every ported timestamp silently renders "Invalid Date" (found on #3 `ActivityTimeline.tsx`; audit the whole class of chatty→CakeCRM date helpers; re-confirmed #15/PR #34).
- `[✓0 ✗0 · 2026-07-24]` **When** naming a new CakeCRM CRM service/tool that writes free-text "notes" → **do** avoid the `log_` verb (use `add_note`/`get_chatter`, matching the `crm_add_note` tool) → **because** `log_*` is already the `activity_log` lane (`crm_log_activity`, the def-less `crm_log_note` back-compat alias, `get_activity_log`); a `log_note` that writes `crm_chatter` reads as if it belongs to activity logging and collides with the alias, forcing a disambiguating comment. Renamed during review-super on #15/PR #34.

## GitHub Actions

Learned building `pr-review.yml` (#11/PR #30): a genericized, optional, advisory AI-review workflow. All exercised in that PR's review-super + settle.

- `[✓1 ✗0 · 2026-07-23]` **When** shipping an OPTIONAL AI/CI workflow that needs a secret → **do** add an explicit has-key gate that exits green when the secret is absent, and never make it a required check → **because** fork PRs never receive secrets, and the auto-issues loop's "required checks green" gate would otherwise hang forever / red-X every fork PR (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** adding `continue-on-error: true` to keep an advisory GitHub Actions check green → **do** also add an `if: always()` terminal-outcome guard that emits `::warning::` + `$GITHUB_STEP_SUMMARY` when no success path ran → **because** `continue-on-error` alone converts a real failure (transient gh/curl/jq death) into a silent green check, indistinguishable from "no findings" (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** gating downstream GitHub Actions steps on a prior step's OUTPUTS with `!= 'value'` → **do** gate on `steps.<id>.outcome == 'success'` and chain each consumer to its DIRECT prerequisite → **because** an unset output (from a failed step) satisfies every `!=` check, so downstream steps fail-OPEN and run against missing/empty files, potentially posting a misleading result (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** capturing `RESPONSE=$(curl ...)` under Actions' default `set -eo pipefail` and branching on the HTTP status → **do** add `|| RESPONSE=$'\n000'` → **because** curl exits non-zero only on TRANSPORT failure (DNS/TLS/timeout), not HTTP 4xx/5xx, so a network blip aborts the step before the status-code handling ever runs (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** writing a multi-clause GitHub Actions `if:` with `||`/`&&` → **do** keep it on ONE physical line, not a YAML `>-` folded block with deeper-indented inner lines → **because** deeper indentation suppresses YAML folding and embeds literal newlines into the expression string — works by luck, brittle (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** truncating a string with `${var:0:N}` that then feeds `jq --rawfile` / JSON → **do** sanitize with `iconv -f UTF-8 -t UTF-8//IGNORE` → **because** the cut can split a multi-byte codepoint, producing invalid UTF-8 that jq rejects — fails only on large non-ASCII inputs, easy to miss (#11/PR #30).
- `[✓1 ✗0 · 2026-07-23]` **When** documenting GitHub branch-protection required checks → **do** use each job's `name:` DISPLAY value, not the job ID → **because** required-status contexts match the displayed check name (#11/PR #30).
- **Verified fact:** GitHub's `GITHUB_TOKEN` posts issue/PR comments (`POST /repos/{o}/{r}/issues/{n}/comments`) with `permissions: pull-requests: write` alone — `issues: write` is NOT additionally required for a PR's comments (confirmed against the working cake_os blueprint + two reviewers on #11/PR #30). Don't cargo-cult `issues: write` onto PR-comment workflows.
